Moonlight 6.2.0 · Windows · 1바이트 패치

부팅 후 첫 연결 실패, 원인은 바이트 하나

방화벽 문제가 아니었다. Windows가 보낸 “잠시 후 다시”(오류 10055)를 Moonlight가 “포기”로 분류한 탓이다. exe 속 규칙표의 1바이트를 바꿔 고쳤다.

대상: Moonlight(Windows 클라이언트) ↔ Sunshine(Linux 호스트) · 같은 LAN 유선

패치 전 첫 연결5/5 실패
패치 후 첫 연결2/2 성공
바꾼 바이트1개
오류 규칙표31칸

1 · 무엇인가

Moonlight는 다른 PC의 게임 화면을 받아 온다

Moonlight는 오픈소스 게임 스트리밍 클라이언트다. 내 Windows PC(Moonlight)가 다른 PC의 서버(Sunshine)에 붙어, 영상·소리를 받고 키보드·마우스 입력을 돌려보낸다. 연결은 통신선 여러 개로 나뉘고, 그중 하나가 명령 채널이다.

2 · 증상

부팅 후 ‘첫 실행’만 실패했다 — 경과 시간과는 무관

부팅한 뒤 Moonlight를 처음 켜면 연결이 오류 -1로 실패하고 “방화벽을 확인하세요”가 떴다. 하지만 같은 부팅에서 두 번째·세 번째로 켜면 늘 정상이었다. 부팅 후 몇 시간이 지났는지는 상관없었다.

실패 직후 돌린 UDP 47999 포트 테스트는 성공했다. 방화벽·포트포워딩은 범인이 아니었다. 부팅 후 세 번의 시도는 매번 같은 순서였다.

① 첫 시도control stream 실패오류 −1 · 10055
② 두 번째RTSP 복호화 실패첫 실패의 여파 (추정)
③ 세 번째정상 연결이후 재부팅까지 문제 없음

3 · 도구

REA는 exe를 읽을 수 있는 코드로 되돌린다

REA(Reverse Engineer Anything)는 AI 에이전트가 바이너리를 역공학하도록 돕는 도구다. Ghidra·IDA·Hopper 같은 분석 엔진을 CLI와 MCP로 연결하고, 결론마다 근거(evidence)를 함께 남긴다. 여기서는 Ghidra를 엔진으로 썼다.

4 · 선택

“REA를 한번 써보고 싶었다”

솔직한 동기는 그거였다 — 새 도구를 직접 써보고 싶었다. 그리고 이 문제는 시험 대상으로 꽤 잘 맞았다.

위치

exe 안에 있다

고칠 규칙표가 설치된 바이너리의 기계어 안에 있어, 소스가 아니라 exe에서 찾아야 했다.

대조

소스로 검증된다

enet의 win32.c가 공개돼 있어, REA가 복원한 case 목록을 원본 소스와 맞춰볼 수 있었다.

난이도

그냥은 안 보인다

오류 상수를 직접 비교하는 코드가 없었다. 컴파일러가 switch를 표로 바꿔둔 탓이다 (→ 6·7절).

5 · 원인

Windows의 “잠시 후 다시”를 Moonlight가 “포기”로 읽었다

명령 채널의 첫 송신이 오류 10055(WSAENOBUFS, “버퍼 없음”)로 실패했다. 이건 일시적인 상태다. 그런데 ENet의 규칙표에 10055가 “다시 시도” 목록에 없어, 재전송 기회도 없이 연결을 끊었다.

패치 전

포기 → 오류창

패치 후

0 반환 → 재전송

6 · 핵심

규칙표의 한 칸을 “포기”에서 “다시 시도”로

컴파일러는 switch(오류코드)를 작은 표로 바꿔둔다. “오류값 − 10035”로 31칸짜리 표에서 0(다시 시도) 또는 1(포기)을 꺼내고, 그 값으로 두 갈래 중 하나로 점프한다. 10055는 21번째 칸(인덱스 20)이고, 원래 값이 1이었다.

바뀌는 건 표의 데이터 한 칸뿐이다. 다른 오류 코드의 처리는 전혀 건드리지 않는다.

7 · 추적

상수가 안 보여서, 바이트 패턴으로 찾았다

오류 상수를 직접 비교하는 코드가 없었다. 그래서 컴파일러가 만든 점프 테이블의 특징적인 바이트를 단서로 삼았다.

이 함수는 send 루프가 인라인된 형태로 보인다 (추정). 어셈블리 주소·근거 ID 같은 세부는 접어 둔다.

기술 세부 (주소·근거)

함수 FUN_1400a9740 (0x1400a9740–0x1400aa51d, 3550바이트). switch 디스패치 0x1400aa34e. 인덱스 테이블 RVA 0xaa528, 점프 테이블 RVA 0xaa520. 외부 호출: WSASendMsg, WSAGetLastError, connect, htons. 근거 파일 rea/FUN_1400a9740.evidence.json.

8 · 패치

해시와 표를 확인한 뒤에만 1바이트를 바꾼다

패치 스크립트는 입력 파일이 아는 버전인지(SHA-256), 표 31바이트가 예상과 같은지 먼저 검사한다. 하나라도 다르면 중단하고, 맞을 때만 인덱스 20 칸을 01 → 00으로 바꾼다.

부작용: Authenticode 서명이 깨진다(로컬 사용엔 무관). Moonlight를 업데이트하면 원본으로 덮어써진다. 되돌리려면 보관해 둔 Moonlight.exe.orig로 덮어쓴다.

# 적용 (관리자 PowerShell, Moonlight 종료 상태)
$dir = 'C:\Program Files\Moonlight Game Streaming'
Copy-Item "$dir\Moonlight.exe" "$dir\Moonlight.exe.orig"
python -I tools\patch_moonlight.py "$dir\Moonlight.exe.orig" "$env:TEMP\Moonlight.patched.exe"
Copy-Item "$env:TEMP\Moonlight.patched.exe" "$dir\Moonlight.exe" -Force

# 롤백
Copy-Item "$dir\Moonlight.exe.orig" "$dir\Moonlight.exe" -Force

9 · 검증

패치 후 부팅 직후 첫 연결 2/2 성공

패치 전

5회 모두 실패

패치 후

2회 모두 성공

정적으로도 확인했다: 원본과 패치본은 정확히 1바이트(0xa993c)만 다르고, 그 표를 참조하는 곳은 switch 하나뿐이다.

남은 위험

표본이 작다. 다시 실패하는데 로그가 timed out으로 나오면, 10055가 10초 넘게 이어진 것이다. 그 경우 QoS를 끄는 방안(ENET_SOCKOPT_QOS 무력화)을 검토한다. 2차 증상이던 RTSP 복호화 실패는 첫 실패가 사라지자 함께 사라졌다 (추정).

10 · 다음

업데이트하면 다시 패치, 또는 소스에서 한 줄

Moonlight를 업데이트하면 해시가 달라 스크립트가 패치를 거부한다. 다음 순서로 다시 찾는다.

  1. 새 exe에서 바이트 패턴 05 cd d8 ff ff 83 f8 1e를 찾는다. 바로 뒤 명령의 RVA가 인덱스 표 위치다.
  2. REA로 그 함수를 분석해 case 목록이 위와 같은지 확인한다.
  3. 표 위치 + 20 바이트를 01 → 00으로 바꾸고, 스크립트의 해시·오프셋·표 상수를 새 값으로 고친다.

업스트림(cgutman/enet)이 WSAENOBUFS를 일시적 오류로 처리하도록 고친 버전을 쓰면, 패치 자체가 필요 없다. 소스에서 직접 고친다면 한 줄이면 된다 — 일시적 오류 목록에 추가한다.

case WSAENOBUFS:   // 10055를 일시적 오류로 처리 → return 0
